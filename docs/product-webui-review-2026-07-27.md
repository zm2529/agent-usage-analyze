## 1. 结论摘要

Agent Usage Analyzer 的产品方向成立：它不是单纯记录 Codex 使用次数，而是尝试完成“工作记录 → 证据解释 → 改进行动 → 效果复盘”的个人工程改进闭环。

当前最有价值的能力是：

- 本地优先，原始会话和分析结果留在本机。
- 将确定性统计与 LLM 语义分析区分开。
- 分析结论带证据来源、适用范围、反例、置信度和原始 LLM 运行信息。
- 能从会话、任务、Skill、工具、模型、推理强度和上下文文档多个角度观察使用行为。
- 已具备把“分析结果”转化为“可执行实验”的数据结构。

综合评价：

- 产品方向：**8/10**。真实解决了重度 Codex 用户“做了很多工作，但难以系统复盘”的问题。
- 当前可信度与闭环完成度：**6/10**。统计口径、运行状态表达和建议效果验证尚未完全闭合。
- 当前最大短板：不是缺少更多分析，而是缺少一个可信、自动、低打扰的“建议是否真的有效”闭环。

优先级建议：

1. 先统一 Token 等关键指标口径，并让 Hook、导入、LLM 队列状态反映真实状态。
2. 再消除加载期间的假空状态、旧报告与新证据混用等信任问题。
3. 最后实现自动建议效果追踪，让产品从“会给建议”升级为“知道建议有没有帮助”。

## 3. 产品定位与功能设计评价

### 3.1 产品定位

最合适的产品定义是：

> 面向 Codex 重度用户的本地个人工程复盘系统，用证据解释工作方式，并自动验证改进建议是否产生正向收益。

它不应被定位成：

- 单纯的 Token 计数器；
- 通用 BI Dashboard；
- 用一个总分评价人的生产力；
- 只输出泛化“最佳实践”的 AI 教练。

产品应持续围绕三个用户问题组织：

1. **发生了什么？** 会话、任务、工具、Skill、模型和成本事实。
2. **为什么值得关注？** 有证据的行为模式、优势、瓶颈和适用边界。
3. **下一步做什么，是否有效？** 可执行建议、自动观察和复盘结论。

### 3.2 正向价值

当前产品已有几项明显优于普通分析工具的设计：

- **证据可追溯**：分析项可以跳转到来源会话，不只给不可验证的结论。
- **承认不确定性**：支持“需要继续观察”“证据不足”“不一定适用的情况”。
- **反例与适用范围**：避免把相关性包装成普遍规律。
- **LLM 可观察性**：可以查看 provider、model、prompt version、耗时、Token、输入摘要、系统提示词和原始结构化输出。
- **本地事实与语义解释分层**：本地结构分析负责事实，LLM 负责跨会话解释。
- **已有实验结构**：行为报告已经包含假设、适用任务、观察指标、护栏和复盘条件。

这些能力确实能带来正向增益，尤其适用于：

- 高频、多项目、长周期使用 Codex 的用户；
- 经常使用子 Agent、Skill 和多种模型配置的用户；
- 希望减少返工、等待、约束遗漏和无效高推理投入的用户；
- 愿意基于证据持续调整工作方式的用户。

### 3.3 当前边界

现阶段分析结果可以作为“值得尝试的假设”，但还不能普遍表述为“已证明能提升效率”，原因是：

- 语义增强只覆盖当前窗口约 6.1% 的会话；
- 24 个代表性样本适合发现模式，不一定足以证明因果；
- 会话类型、任务难度、项目差异会影响结果；
- 当前没有稳定的建议前后对照 cohort；
- 缺少对交付质量、返工和人工介入等结果指标的持续跟踪。

因此，产品文案应使用“观察到”“可能有帮助”“建议尝试”，避免使用“已经提升”“最佳方式”等因果性表达。

## 4. “统计”功能专项 Review

### 4.1 做得好的地方

- 最近 7 天、今天、最近 30 天的时间范围易理解。
- 会话、主任务、子 Agent、工具、Skill、Token 和提示词质量覆盖了主要使用维度。
- 活动节奏使用按日或小时的非累计趋势，能看到波动。
- 模型与推理强度分布有助于发现过度使用高成本配置。
- 页面明确说明数据来自本机记录。

### 4.2 P0：Token 统计契约不一致

当前后端趋势数据将缓存 Token 从输入 Token 中扣除：

- `server/src/routes/analytics.ts:172-188`

但总计数据直接累计完整 `input_tokens`，同时又单独累计缓存写入和缓存读取：

- `server/src/routes/analytics.ts:296-308`

前端构造 Token 组成图时，把完整输入、输出、缓存写入、缓存读取作为四个并列项相加：

- `dashboard/src/pages/DashboardPage.tsx:98-103`

而顶部指标文案又写成“输入（其中缓存）”：

- `dashboard/src/pages/DashboardPage.tsx:159-165`

这会产生三个问题：

1. 趋势图和总计使用不同口径。
2. Token 组成图可能把缓存重复计算。
3. 用户无法确认“输入 Token”是否包含缓存。

建议定义唯一数据契约：

```text
uncachedInputTokens
cacheCreationTokens
cacheReadTokens
outputTokens
totalProcessedTokens =
  uncachedInputTokens + cacheCreationTokens + cacheReadTokens + outputTokens
```

如果底层 `input_tokens` 已包含缓存，则在服务端完成一次归一化，前端不再推断或相减。

验收标准：

- 总计等于各组成项之和。
- 趋势总和与顶部总计在同一时间范围内一致。
- Tooltip、标题和 API 字段使用相同定义。
- 为“底层输入包含缓存”和“不包含缓存”各补一个契约测试。

### 4.3 P1：统计值缺少解释上下文

建议补充：

- “提示词质量 75”旁展示“已分析 N/M 个会话”，避免把小样本均值当成总体。
- 会话数拆分为根会话、子 Agent 会话或其他会话。
- “累计时长”明确说明会话可能重叠，不代表人工投入时长。
- Token 同时提供绝对值、每任务中位数、每有效交付 Token。
- 工具调用同时提供每任务分布，避免少数超长会话拉高总量。

### 4.4 P2：统计页面应从“报表”转向“变化解释”

当前 Dashboard 信息完整但偏长。首页应优先展示：

1. 相比上一周期发生了什么变化；
2. 哪个变化值得关注；
3. 可能原因是什么；
4. 建议查看或尝试什么。

完整分布和明细继续保留为下钻内容。

推荐首页首屏结构：

```text
本周期摘要
├─ 3 个最重要变化
├─ 1 个需要关注的风险
├─ 1 个建议实验及追踪进度
└─ 数据健康与更新时间

详细统计
├─ 活动节奏
├─ Token
├─ 工具 / Skill
└─ 模型 / 推理强度
```

## 5. “分析”功能专项 Review

### 5.1 分析结果是否有正向增益

有，但价值来自“可操作和可验证”，不是来自文字数量。

本轮实际报告提出的方向包括：

- 继续保持证据驱动的交付方式；
- 把关键约束前置，减少后期返工；
- 用简短的决策胶囊记录关键决策；
- 让子 Agent 编排与任务边界更匹配；
- 对 Skill 组合进行小规模实验。

这些方向与真实工作过程有合理对应关系，能促成更一致的任务启动、交付验证和协作边界，具备正向增益潜力。

但建议必须满足以下条件才算“产品价值”：

- 用户能理解为什么得到这条建议；
- 能看到建议适用于哪些任务；
- 系统能在后续会话中自动观察；
- 能区分未采用、未观察到和证据不足；
- 能给出复盘结论和置信度；
- 结论能链接回前后证据。

如果缺少后半段，建议页会退化成“看起来正确但无法证明有用”的 AI 文案集合。

### 5.2 P0：运行状态不够真实

顶部 Hook 状态根据导入能力推断，而不是读取真实 Hook 状态：

- `dashboard/src/components/layout/Header.tsx:86-104`

LLM 状态只要存在行为报告就显示“异步就绪”：

- `dashboard/src/components/layout/Header.tsx:112-115`

但 review 时队列仍有 39 个“等待能力”和 14 个失败项。因此“报告存在”不能代表“LLM 链路健康”。

建议将状态拆为：

- Hook：已安装 / 已收到最近事件 / 长时间未收到事件 / 未连接。
- 导入：空闲 / 扫描中 / 最近成功 / 最近失败。
- 会话语义分析：已完成 / 排队 / 等待能力 / 失败。
- 跨会话报告：最新 / 有新证据待更新 / 生成中 / 生成失败。

每个状态都应显示：

- 最近成功时间；
- 当前积压数量；
- 失败数量；
- 可执行的处理入口。

### 5.3 P0：加载期间会短暂显示假空状态

`ImprovePage` 读取行为报告后，未在主要内容渲染前统一处理 `state.isLoading`：

- `dashboard/src/pages/ImprovePage.tsx:85-115`
- `dashboard/src/pages/ImprovePage.tsx:145-156`

行为报告接口在本地大数据库下约需 6 秒。加载阶段可能先显示：

- 等待首次分析；
- 0 个样本；
- 尚未生成使用分析。

随后才切换为真实报告。这会直接伤害用户对分析数据的信任。

建议：

- 加载期间只显示稳定骨架屏，不显示 0、空、未生成等业务状态。
- 将“大型完整报告”和“轻量状态摘要”拆成两个接口。
- 轻量接口只返回版本、生成时间、覆盖率、队列和摘要卡片。
- 完整报告延迟加载，或在生成完成时物化缓存。

### 5.4 P1：报告版本和证据时间需要贯穿所有页面

Review 初次观察时，页面展示旧版 `behavior-report-v6`，代码当前版本为 `v9`，页面提示需要重新生成。随后自动分析已经生成 `v9`，当前该运行时问题已恢复。

现有行为报告接口能够识别当前版本和兼容旧版本：

- `server/src/routes/behavior-report.ts:21-59`
- `cli/src/analysis/behavior-report.ts:13`

但建议接口直接读取“最近一条成功的行为报告”，没有按当前 prompt version 过滤：

- `server/src/routes/advice.ts:24-30`

这意味着未来再次升级 prompt 时，行为分析页可能提示报告已过期，但建议页仍继续展示旧报告生成的建议。

建议所有派生页面统一展示并校验：

- 报告版本；
- 证据截止时间；
- 生成时间；
- 是否存在更新证据；
- 是否为兼容旧版结果；
- 语义覆盖率和代表性样本数。

过期建议可以暂时展示，但必须标为“基于旧版分析，等待刷新”，不能与最新建议混合。

### 5.5 P1：报告证据与当前重算数据可能混用

行为分析页上方的报告摘要优先使用生成报告时的 `inputSummary`，但 Skill、工具等部分可以使用当前重新计算的 dataset：

- `dashboard/src/pages/ImprovePage.tsx:96-115`
- `dashboard/src/pages/ImprovePage.tsx:174-181`

这会让一个页面同时出现：

- 基于旧证据窗口生成的 LLM 结论；
- 基于当前数据库计算的新统计。

建议在页面上明确区分：

- **报告快照**：生成时锁定的证据窗口与统计。
- **当前监测**：报告生成后新增的事实。

只有重新生成后，新的当前监测数据才进入报告快照。

### 5.6 P2：分析页面内容密度过高

当前行为分析页覆盖画像、优势、瓶颈、习惯、Skill、工具、模型、推理强度、上下文文档、Token 和发展计划，信息很丰富，但用户难以快速判断“现在最该做什么”。

建议分成三层：

1. **本次最重要结论**：最多 3 条，注明变化与证据。
2. **建议实验**：最多 1–3 个，显示自动追踪状态。
3. **完整分析档案**：画像、工具、模型、上下文等专题下钻。

## 6. “建议”功能与效果追踪设计

### 6.1 当前已有能力

行为报告的数据结构已经包含完整实验字段：

- `eligibleCohort`：适用任务；
- `observableOutcome`：观察指标；
- `guardrail`：护栏；
- `reviewAfter`：复盘条件；
- `evidenceRefs`：证据。

位置：

- `dashboard/src/lib/types.ts:563-576`

但建议接口将实验压缩成：

- 标题；
- 假设；
- 适用任务。

位置：

- `server/src/routes/advice.ts:32-57`

观察指标、护栏、复盘条件和证据引用因此丢失。建议页的战略建议也是只读卡片：

- `dashboard/src/pages/AdvicePage.tsx:60-86`

当前建议页可以展示建议，却没有完成“建议 → 观察 → 复盘”的闭环。

### 6.2 用户不应被要求逐项主动选择

以下字段默认都可以由系统自动建立或从后续会话分析中推断，不应要求用户逐项填写：

| 字段 | 推荐方式 | 重要限制 |
| --- | --- | --- |
| 开始采用 | 从后续适用任务中检测目标行为，标记“观察到采用信号” | 只能判断行为证据，不能推断用户主观意图 |
| 暂不采用 | 不建议仅凭未出现自动判定 | 应显示“尚未观察到”或“证据不足”，而不是“用户拒绝” |
| 适用任务 | 建议生成时自动定义，后续按任务类型、范围、工具、会话结构匹配 | 允许用户纠正错误匹配 |
| 观察指标 | 建议生成时自动创建 | 必须是现有事件可测量的指标 |
| 护栏 | 按建议类型使用默认模板，由模型补充 | 护栏触发时不能只看主指标改善 |
| 复盘日期 | 使用时间窗口或累计 N 个适用任务自动计算 | 优先采用“样本数 + 最长时间”双条件 |
| 改善 / 无改善 / 不确定 | 自动比较基线与后续 cohort | 必须展示样本量、效应方向、置信度和干扰因素 |

默认原则：

> 系统自动观察，用户只在系统判断错误时纠正。

### 6.3 推荐状态模型

```text
建议已生成
  → 自动观察中
  → 匹配到适用任务
  → 观察到行为变化 / 尚未观察到
  → 累积结果证据
  → 达到复盘条件
  → 改善 / 无明确改善 / 证据不足
  → 继续观察 / 调整建议 / 结束实验
```

不要把“开始采用 / 暂不采用”作为必选按钮。更准确的系统状态是：

- `observing`：自动观察中；
- `eligible-task-found`：已匹配适用任务；
- `adoption-signal-observed`：观察到采用信号；
- `adoption-not-observed`：尚未观察到；
- `review-ready`：达到复盘条件；
- `improved`：观察到改善；
- `no-clear-improvement`：没有明确改善；
- `insufficient-evidence`：证据不足；
- `guardrail-triggered`：护栏触发；
- `manually-corrected`：用户纠正系统判断。

这里应刻意避免 `rejected` 或 `not-adopted`，除非用户明确表达拒绝。

### 6.4 自动效果评估方法

每条建议生成时创建一个 `AdviceExperiment`：

```text
建议假设
适用任务匹配规则
目标行为信号
主观察指标
护栏指标
基线窗口
后续观察窗口
最小样本数
最长等待时间
证据引用
分析版本
```

自动评估过程：

1. 从建议生成前的相似任务建立 baseline。
2. 新会话稳定导入后，判断是否属于适用任务。
3. 从会话和任务证据中检测目标行为是否出现。
4. 累积主指标和护栏指标。
5. 达到最小样本数或最长等待时间后自动复盘。
6. 输出结论、效应方向、样本数、置信度和前后证据。

建议结果只使用三类主结论：

- **观察到改善**：主指标改善，且护栏没有明显恶化。
- **未观察到明确改善**：样本足够，但改善不明显或结果相互抵消。
- **证据不足**：适用任务过少、行为信号不明确或数据缺失。

“无改善”不应轻易等同于“建议无效”，因为任务难度和项目差异可能造成混杂。

### 6.5 推荐 UI

建议卡片默认展示：

```text
前置关键约束
自动观察中

已匹配 3 / 10 个适用任务
2 个任务观察到采用信号

```

用户交互只保留：

不要求用户手动维护采用状态、指标、护栏和复盘日期。

## 7. 性能与可用性

本轮本地 API 粗略耗时：

| 接口 | 耗时 | 评价 |
| --- | ---: | --- |
| `/api/analytics/overview?range=7d` | 约 5.15 秒 | 首页偏慢 |
| `/api/behavior-report` | 约 6.31 秒 | 容易触发假空状态 |
| `/api/advice` | 约 0.018 秒 | 良好 |
| `/api/sessions?limit=8` | 约 0.75 秒 | 可接受但仍可优化 |

建议：

- 将首页统计预聚合或物化，按数据版本失效。
- 行为报告拆分 summary 与 detail。
- 对大 JSON 使用服务端缓存和 ETag。
- 页面路由级拆包，重型图表按需加载。
- 为大数据库建立性能基线测试，例如 P95：
  - 首页摘要 < 500 ms；
  - 行为报告摘要 < 300 ms；
  - 完整行为报告 < 1.5 s；
  - Sessions 首屏 < 500 ms。

## 8. 分阶段优化路线

### P0：先恢复数据与状态可信度

1. 统一 Token 统计契约并补测试。
2. Hook、导入、会话分析、跨会话报告分别展示真实状态。
3. 为行为报告增加完整加载骨架，消除假空状态。
4. 建议接口只使用当前兼容版本，或明确标记旧版建议。

完成标准：

- 同一指标在顶部、图表和 API 中一致。
- 页面不再把“有报告”等价为“队列健康”。
- 慢请求期间不显示错误的 0 或“未生成”。
- 旧版建议不会无提示地混入当前结果。

### P1：建立自动建议效果追踪

1. 保留并透传实验的完整字段。
2. 创建建议实验、适用任务匹配和行为信号检测。
3. 自动建立 baseline 与后续 cohort。
4. 输出改善、无明确改善、证据不足和护栏触发。
5. 用户只负责纠正错误判断。

完成标准：

- 一条建议无需用户配置即可进入“自动观察中”。
- 新适用任务完成后自动更新追踪进度。
- 达到条件后自动产生可追溯的复盘结果。
- 未观察到行为不会被表述为用户拒绝。

### P2：优化信息架构和性能

1. 首页优先展示变化、原因和下一步。
2. 行为分析页分为摘要、实验和完整档案。
3. 为提示词质量、时长和会话数补足口径说明。
4. 拆分大前端包并优化慢查询。

完成标准：

- 用户进入首页 10 秒内可以回答“本周期最值得关注什么”。
- 用户进入分析页可以直接看到正在追踪的 1–3 个实验。
- 明细仍可下钻，但不占据首屏决策空间。

## 9. 建议的北极星指标

不建议使用“会话数”“Token 数”或“建议阅读数”作为北极星指标。

更合适的是：

> 每 30 天，产生至少一条经后续任务证据支持、且护栏未恶化的有效改进建议。

辅助指标：

- 建议自动进入观察的比例；
- 适用任务匹配准确率；
- 达到复盘条件的建议比例；
- 有前后证据的复盘比例；
- 用户纠正系统判断的比例；
- “证据不足”而非强行下结论的比例；
- 建议带来的返工、等待、人工介入或验证缺失变化。

## 10. 最终判断

项目已经具备一个优秀个人工程分析产品的核心骨架，尤其是本地优先、证据追溯、不确定性表达和 LLM 透明度。

下一阶段不应继续横向增加更多统计维度，而应集中解决两件事：

1. **让每个数字和系统状态可信。**
2. **让每条建议自动被后续会话验证。**

完成这两点后，产品会从“Codex 使用分析 Dashboard”真正升级为“能够持续改善个人工程工作方式的本地智能系统”。
